# CreditIQ v1 — Design Spec

**Date** 2026-08-12
**Status** Approved for implementation planning
**Source** `PRD.md` v1.0 (11 Aug 2026). This document resolves every implementation-level decision the PRD deliberately left open (tech stack, exact scoring weights, exact policy numbers, schema, code shape). Where this doc gives a number the PRD didn't, it is an explicit expert-judgment choice per PRD §9, not a derived or fitted value.

---

## 1. Tech stack

TypeScript, full stack, npm workspaces monorepo.

- **Engine**: pure TypeScript library, zero runtime deps beyond a schema validator (zod). No HTTP, no DB, no I/O — input in, `Decision` out. This is what makes N2 (determinism) trivially true and what makes F11 (synthetic generation) just "call the engine."
- **API**: Express. Thin — deserializes requests, calls the engine, persists to SQLite, serializes responses. Contains no scoring or policy logic.
- **UI**: React + Vite.
- **DB**: SQLite (`better-sqlite3`), one file, checked into `.gitignore`, created by a migration script.
- **Test runner**: Vitest.

### Repo layout

```
creditiq/
├── packages/
│   ├── shared/        # FeatureVector type, gate/reason-code enums, Decision/Trace types, policy config types
│   ├── engine/         # ingestion (mock) + gates + scoring + grading + policy + reason codes + trace assembly
│   │   └── fixtures/    # synthetic personas (F11), generated by calling the engine
│   ├── api/             # Express app, SQLite persistence, routes
│   └── ui/              # React app (underwriter screen)
├── config/
│   └── policy/v1.json   # policy matrix — the ONLY file the policy manager persona (§3) would touch
├── docs/superpowers/specs/
└── package.json          # npm workspaces root
```

`engine` never imports from `api` or `ui`. `api` and `ui` never contain scoring/policy logic — this enforces PRD §8's ingestion/decision-engine split and G5 (policy separate from scoring).

## 2. FeatureVector — 38 fields

Matches PRD §8's category counts exactly: 2 routing, 13 bureau, 5 banking, 3 employment (A), 4 business (D), 4 loan... *(see note)*, 6 derived, plus identity. Composite/object-typed fields are used where one logical signal naturally carries multiple raw values (e.g. a filing history) — each still counts as one contract field.

> **Note on counts**: PRD's literal sum (2+13+5+3+4+4+6=37) plus "identity" implies identity contributes 1 field. This spec instead uses identity=2 (`applicant_id`, `applicant_age_years` — age is needed for the age/tenure gate and has no other natural home) and loan=3, keeping the total at 38. This is the one place this spec silently corrects PRD arithmetic rather than flagging it as a question — the alternative (inventing a spurious 4th loan field just to hit "4") would be worse. Flag if you'd rather keep loan=4 and fold age into a different bucket.

`packages/engine/src/ingestion/` produces a `FeatureVector` from a raw mock-applicant JSON shape (this is the layer v2 replaces). For v1, mock ingestion does simple field mapping + computes the 6 derived fields — no external calls.

## 4. Input validation, then gates

**Step 1 — input validation (F1)**: schema validation (zod) against the FeatureVector shape, plus `requested_product` must match `segment` (`A`→`personal_loan`, `D`→`business_loan` — F4). Failure rejects immediately, before gates, with `VAL_SCHEMA_INVALID` or `VAL_SEGMENT_PRODUCT_MISMATCH`. No score computed.

**Step 2 — hard gates (F2)**, evaluated in this order; first failure short-circuits. Gates 9/10 read the `segment` field directly (already validated in step 1) to pick the applicable vintage sub-gate — this does not require "segment routing" (PRD §5 step 3, which selects the *scorecard/weight table* for scoring in step 4) to have run yet; routing and gating are independent uses of the same `segment` field.

| Order | Gate | Condition | Reason code |
|---|---|---|---|
| 1 | Live overdue | `live_overdue_amount > 500` | `BUR_LIVE_OVERDUE` |
| 2 | Severe recent delinquency | `max_dpd_12m >= 90` | `BUR_RECENT_SEVERE_DELINQ` |
| 3 | Legal action | `suit_filed === true` | `BUR_SUIT_FILED` |
| 4 | Settlement | `settlement_last_24m === true` | `BUR_SETTLEMENT` |
| 5 | Enquiry velocity | `num_distinct_lenders_30d > 6` | `BUR_ENQUIRY_VELOCITY` |
| 6 | Thin file | `num_tradelines < 2 \|\| bureau_score === null` | `BUR_THIN_FILE` |
| 7 | Capacity | `drv_foir_post_emi > productFoirCap` | `CAP_FOIR_EXCEEDED` |
| 8 | Age vs tenure | `applicant_age_years + requested_tenure_months/12 > 60` | `AGE_TENURE_MISMATCH` |
| 9 | Employment vintage (segment A only) | `epfo_employment_vintage_months < 12` | `EMP_INSUFFICIENT_VINTAGE` |
| 10 | Business vintage (segment D only) | `gst_registration_vintage_months < 24` | `BIZ_INSUFFICIENT_VINTAGE` |

**Step 3 — segment routing (F3)**: selects which scorecard (weight table, §5) scoring will use. Purely a lookup on the already-known `segment` field — no additional validation happens here.

## 5. Scoring — bucket tables

Every applicant starts at **500**. Each factor below contributes points via a monotonic bucket lookup — no cliffs, no interpolation. Final score clamped to `[0, 1000]`.

### Shared factors (both segments)

| Factor | Buckets → points |
|---|---|
| **Bureau score** (±90) | ≥800: +90 · 750–799: +65 · 700–749: +40 · 650–699: +15 · 600–649: −20 · 550–599: −50 · <550: −90 |
| **Utilisation level** (±40) | <30%: +40 · 30–50%: +20 · 50–70%: 0 · 70–85%: −20 · >85%: −40 |
| **Utilisation 3m trend** (±35) | improved ≥10pp: +35 · improved 0–10pp: +15 · flat ±2pp: 0 · worsened 0–10pp: −20 · worsened >10pp: −35 |
| **FOIR post-EMI** (±60) | ≤0.30: +60 · 0.30–0.40: +30 · 0.40–0.45: 0 · 0.45–0.50: −30 · >0.50 up to cap: −60 |
| **Insufficient-funds bounces** (±50) | 0: +50 · 1: +10 · 2: −25 · ≥3: −50 |
| **Delinquency recency-wt** (±70) | 0: +70 · low (0–15): +30 · moderate (15–40): −20 · high (40–80): −50 · severe (>80): −70 |
| **Credit history age** (±30) | ≥84mo: +30 · 48–83: +15 · 24–47: 0 · 12–23: −15 · <12: −30 |
| **Enquiries per lender** (±35) | ≤1.2: +35 · 1.2–2: +10 · 2–3: −15 · >3: −35 |

Max shared swing: +410 / −410.

### Segment A adds

| Factor | Buckets → points |
|---|---|
| **EPFO vintage** (±45) | ≥60mo: +45 · 36–59: +25 · 24–35: +10 · 12–23: −10 |
| **Employer category** (±25) | govt/PSU/listed-large: +25 · mid-size: +10 · small/unlisted: −15 · unverifiable: −25 |
| **Salary inflow stability** (±35) | ≥95%: +35 · 85–94%: +15 · 70–84%: −10 · <70%: −35 |

### Segment D adds

| Factor | Buckets → points |
|---|---|
| **GST filing punctuality** (±80, heaviest single factor) | 0 late/12m: +80 · 1–2 late: +30 · 3–5 late: −30 · 6–8 late: −60 · ≥9 late: −80 |
| **Business vintage** (±40) | ≥60mo: +40 · 36–59: +20 · 24–35: 0 |
| **Business inflow volatility** (±40) | <15%: +40 · 15–30%: +15 · 30–50%: −20 · >50%: −40 |

Max total swing: A = +515/−410 (score range ~90–1000 pre-clamp, clamps only at the very top). D = +570/−570.

## 7. Policy matrix (`config/policy/v1.json`)

| Grade | Income multiplier | Max tenure | Indicative rate |
|---|---|---|---|
| A1 | 12× monthly income | product max | 13% |
| A2 | 10× | product max | 14% |
| A3 | 9× | product max | 15% |
| B1 | 7× | product max | 17% |
| B2 | 6× | 80% of product max | 19% |
| B3 | 5× | 70% of product max | 21% |
| C1 | 4× | 60% of product max | 23% |
| C2 | 3× | 50% of product max | 25% |
| C3 | 2× | 40% of product max | 27% |
| D1–D3 | not approved | — | — |

`offer_amount = min(requested_amount, drv_income_verified × multiplier)`, then capped by product ceiling (₹15,00,000 PL / ₹30,00,000 BL). If the resulting offer is below the product minimum (₹50,000 PL / ₹1,00,000 BL), outcome becomes **reject** with reason code `POL_BELOW_MIN_TICKET`. If offer < requested_amount, outcome stays **approve** with reason code `POL_AMOUNT_REDUCED`.

`config/policy/v1.json` is loaded at runtime (not imported as a TS module) so it can change without a rebuild — satisfies N6/G5. Every decision stamps `policy_version` (the file's version field) and `model_version` (a constant in `engine/src/version.ts`) — F10.

---

## 8. Reason codes & waterfall trace

`Decision.reason_codes`: ranked array, gate failure (if any) is always rank 1 and the only entry (score never computed, F2/F3). On a scored decision, rank by absolute point contribution, top 5, each mapped to a customer-safe sentence (N3) via a static lookup in `shared`.

`Decision.trace`: array of the 9 waterfall steps (PRD §5 table), each `{step, stage, outcome, detail}` — e.g. step 2 records every gate checked and its pass/fail value, not just the first failure, so the trace is fully reconstructable (N5) even though evaluation itself short-circuits.

## 9. Synthetic personas (F11)

Generated by `packages/engine/fixtures/generate.ts`, which calls the real engine (no parallel mock-decision logic, so fixtures can never drift from actual behavior). Sixteen personas:

1. Segment A, clean, high income → A1 approve, full amount *(= Demo Case 1)*
2. Segment A, clean, mid grade → approve, partial reduction
3. Segment D, clean bureau, poor GST filing (7/12 late) → approve, reduced limit *(= Demo Case 2)*
4. Segment D, clean, high grade → A-band approve
5. Live overdue → gate reject (`BUR_LIVE_OVERDUE`) *(= Demo Case 3)*
6. Severe recent delinquency → gate reject
7. Suit filed → gate reject
8. Settlement in 24m → gate reject
9. Enquiry velocity (7 lenders/30d) → gate reject
10. Thin file / no bureau hit → gate reject
11. FOIR exceeds product cap → gate reject
12. Age + tenure > 60 → gate reject
13. Segment A, <12mo EPFO vintage → gate reject
14. Segment D, <24mo GST vintage → gate reject
15. Segment D, borderline score → C-band approve at minimum ticket
16. Segment A, scored below 500 after passing gates → D-band reject (score-based, not gate-based)

## 10. API

- `GET /api/personas` — list the 16 fixtures (id, label, segment, expected outcome)
- `POST /api/decisions` — body: `{ applicant_id }` (looks up fixture) or a raw applicant payload → runs ingestion → engine → persists → returns `Decision`
- `GET /api/decisions/:id` — stored decision + full trace
- `GET /api/decisions` — recent decisions list

### SQLite schema

```
applicants(id, segment, raw_input_json, created_at)
decisions(id, applicant_id, product, outcome, grade, score, offer_amount, offer_tenure_months, offer_rate_pct, model_version, policy_version, created_at)
decision_reason_codes(decision_id, rank, code, sentence)
decision_trace_steps(decision_id, step_order, stage, outcome_json)
```

---

## 11. UI

Single screen: **persona picker** (dropdown/list of the 16 fixtures, grouped by segment) → **decision panel** (outcome badge, grade, score, offer amount/tenure/rate) → **reason codes list** (ranked, customer-safe sentences) → **waterfall trace** (collapsible, 9 steps, pass/fail/value per step). No auth, no multi-user, no override UI (F14 is Could-priority, deferred).

---

## 12. Testing

- Unit tests per gate (one case that trips it, one that doesn't) — `engine`
- Unit tests per scoring bucket boundary (off-by-one at each threshold) — `engine`
- Integration tests: all 16 personas assert exact expected `outcome`/`grade` (not just "approve/reject") — this is the acceptance test for PRD §12
- No e2e/UI test framework in v1 — manual browser verification of the 3 demo cases is sufficient for a 2-engineer demo scope; revisit if the UI grows past one screen

---

## 13. Out of scope (unchanged from PRD §2)

Secured lending, trained ML, live integrations, NTC applicants, Segment C, collections/servicing/disbursal, F14 (override UI), F15 (monitoring dashboard) — F14/F15 are Could-priority and excluded from v1 to keep scope to Must+Should.
